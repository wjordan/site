Predicting the Go linker

September 2, 2026

Edit one line of a Go program and the linker regenerates half the binary, because most of a Go executable is tables derived from the function list. Presage predicts nearly all of those changes from the old binary. For a one-line edit in a 30 MB program, its patch is 1.1 KB versus 150 KB for bsdiff.

A Presage patch tells the decoder how to predict the new binary from the old one, and supplies a correction for the bytes the decoder gets wrong. It halved the patch Chrome's own updater ships. Go suits it better, because the linker derives more of the file, by rules simple enough to follow exactly.

What the linker derives

Less than half of a Go binary is code. Here’s the breakdown for stripped Prometheus 3.13.2.

The runtime’s symbol table, .gopclntab, holds each function’s name and address and maps instructions to source lines, stack depths and pointer maps. The runtime needs it for stack traces and garbage collection, so stripping leaves it alone. .rodata holds the type descriptors, which name their methods and element types by offset.

None of it survives a build. The linker lays out the code package by package, then regenerates every table from the result. Grow one function and every function after it moves, along with every table entry that names an address. A byte-level differ finds the moved code, but it can't know that a 35 MB table is a function of the function list, so it ships the differences.

What one line does

Add w.Header().Set("X-Foo", "bar") to one HTTP handler of a 30 MB program. The handler grows by 192 bytes. It lives in main, which the linker lays out last, so only the functions after it move. Still, 14% of the file's bytes change, and under 200 of them are the compiled edit.

Nearly all of the rest is offsets moved by constants. Each function's tables sit in one shared blob, and its record holds the offset of each. The edited function’s tables grew by 34 bytes.

In every function record after it, the entry offset increases by 192 and three table offsets increase by 34. The same two numbers account for every change in the function index, the stack maps and the type descriptors. A decoder holding the old binary and those two numbers can predict all of it.

Predicting it

That is what presage's Go module does. The plan records additions, removals and size changes relative to the old function list, along with any shifts in the data sections. Here that is one resized function.

From the plan and the old binary, the decoder predicts the whole new file. It copies each function to its new address and re-targets every PC-relative operand. It regenerates .gopclntab, rewrites the offsets in the type descriptors, and recomputes the ELF headers and the FIPS integrity HMAC the runtime checks at startup. Edited functions are predicted in pieces from anywhere in the old code, since the compiler emits the same sequences for the same constructs.

The encoder runs the same prediction and ships a correction for the bytes that differ from the real binary. Here the correction is 330 bytes, mostly the compiled edit and two build-ID notes. With the plan and hashes, the patch is 1,100 bytes. A wrong prediction only costs bytes, because the decoder checks the result's hash before anything uses it.

A release

Prometheus 3.13.1 to 3.13.2 edits two source files and bumps a few dependencies. Fewer than a hundred of its 114 thousand functions are added or resized, yet 84% of the file's bytes change.

rsync requires byte-for-byte block matches, so a changed displacement every few dozen bytes forces it to send most of the file. xdelta3 and bsdiff find the slide and still pay for the displacements. Zucchini would translate them, but it doesn't recognise a Go binary and patches it raw. New functions, their table entries and resized function bodies account for the sixth of a percent the prediction misses. Encoding takes four seconds, applying one.

The advantage shrinks as builds drift apart. The next minor release, 3.14.0, adds six thousand functions and resizes hundreds more; its patch is 4.8 MB against bsdiff's 9.8 MB, half where the patch release was a thirtieth.

Debug information

Upstream ships Prometheus unstripped, with 38 MB of symbol tables and compressed DWARF on top, and there the same patch release costs bsdiff 28 MB. Debug information is full of code addresses, and a compressed stream whose input changes near its start differs from there to its end. But DWARF is derived from the function list too. Presage unwraps the compression, predicts the DWARF from the function map it already built, and recompresses with the linker's compressor. The patch is 468 KB; the one-line change with debug information is 1.9 KB.

Which linker

The prediction is exact because it models one linker, so it has to follow that linker. Go 1.27 moved the type descriptors into their own section and replaced the debug compressor, and a model of 1.26 gets a 1.27 binary wrong from the first descriptor. The Go module models the release the binary says it is, 1.26 or 1.27 today, and otherwise falls back to the generic ELF module that patched Chrome.
